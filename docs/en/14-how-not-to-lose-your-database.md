# How not to lose your database

If you are going to obsess over one thing at the start, let it be this.

## How databases get lost in small projects
- deploying migrations without backup
- deleting “test data” that was not actually test data
- changing connection variables without checking environment
- resetting volumes or containers without understanding impact
- running destructive scripts generated by AI
- accidentally pointing local or staging work at production

## Minimum rules

### 1. Before touching DB, back up first
Not after. Before.

### 2. Never run destructive scripts blindly
If you see `DROP`, `TRUNCATE`, mass `DELETE`, or reset commands, stop.

### 3. Do not mix deploy and migration without thinking about rollback
Code and data do not recover the same way.

### 4. Identify the environment you are touching
Local, staging, and production are not the same thing.

## What to verify first
- database name
- host
- user
- whether you are in production or not
- whether a recent restorable backup exists
- whether the migration has a way back
- whether the script changes data or only structure

## What to ask AI
Before running anything DB-related, ask:
- which tables it touches
- whether the change is destructive or not
- whether it requires a migration
- how to revert it
- what to validate afterward
- what happens if it fails halfway through

## Minimum validation after changes
- the app connects
- the main flow works
- expected tables and columns still exist
- data was not emptied by mistake
- connection variables still point to the correct environment

## Alarm signals
- you do not know whether you are in staging or production
- the backup exists but nobody has ever restored it
- you are about to run a script you do not fully understand
- the DB change is bundled with 10 unrelated changes

## Final rule
You can rebuild a lot of code.
Your real data is a different story.
Treat the database as the most sensitive part of the project.
